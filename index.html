One boot, in order

The Loader starts every Service and Controller in dependency order and the Scheduler runs their updates. One broken module logs an error instead of stopping the game.

Validated networking

Every message lives in one list. Net checks argument types, ranges and rate limits before any handler runs.

Server-authoritative state

Player values are replicated to the right audience only, and the client watches them with State.Observe.

Saving that survives retries

Session-locked player data with versioned migrations, plus Robux purchases that are granted exactly once.

What Keel is ​

Keel is the framework behind my Roblox games. It is a set of Luau modules (Loader, Scheduler, Net, Defs, Entity, Data, State, Replica, a client UI layer, an admin Console and Purchases) plus a small starter game, a unit-test runner and a tool, tools/keel.js, that puts all of it into a game and updates it later.

It is built for Roblox Studio's Script Sync and GitHub only. There is no Rojo, no Wally and no package manager: Keel's files go to fixed places in your game and keel.js copies them there.

Why it exists ​

  • Bugs get fixed once. A game never edits Keel. A fix is made in the Keel repo, tagged, and installed into each game with node tools/keel.js update <tag>.
  • A new game starts with the hard parts working. Loading, saving, networking, purchases and an admin console are already there.
  • The server is the authority. The client sends what it wants to do; the server decides. Net validates every message before a handler sees it.
  • Typos are caught early. Keel is --!strict, game data is checked against typed shapes at boot, and the Loader refuses dependency cycles and unknown names.
