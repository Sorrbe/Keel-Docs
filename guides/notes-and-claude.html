Notes and Claude ​

Every Keel game keeps its notes in Docs/, an Obsidian vault, with one layout shared by all games. The layout, a few hooks and a set of skills let Claude Code pick up the project in a new chat by reading a few small notes instead of the whole vault, and keep those notes true as the code changes.

The vault layout ​

A new game gets the skeleton from Starter/Docs/ (empty tables and headings, copied once by keel.js new; the game owns them from then on).

WhereWhat goes in itSource of truth?
Docs/Start Here.mdThe hub: every note linked with a one-line description. Claude reads it first—
Docs/Status.mdWhere the build is: Current, Last and Next, one or two lines each—
Docs/Done.mdEvery finished piece of work, newest last. Status's Last is always its last row—
Docs/Look Later.mdSide notes, open decisions, before-launch tasks. Claude opens it only when pointed there—
Docs/Systems/How the code is built: one note per system, Game Already Exists (the game's reusable code) and Game Tooling (its own hooks). Keel's notes are in Systems/Keel/, read-only. A system with several notes gets its own subfolderYes, for code
Docs/Design/Settled game design. Design Index (table of contents), Design Status, System Spec TemplateYes, for design
Docs/Brainstorm/Ideas, research, drafts, rejected options. Brainstorm Status lists themNo
Docs/Completed Build Orders/Finished build plans, ignored by GitNo

During feature work Claude reads only Systems/ and Design/; Brainstorm/ is opened only when you point to a note.

How notes stay current ​

  • code: lists. Every Systems/ note lists the files it documents in its frontmatter (a path ending in / covers a folder).
  • note-lookup (after each edit) tells Claude which notes list the edited file, so it opens only those.
  • docs-check (when Claude ends a turn) flags uncommitted src/ files whose notes are older than the code, or that no note lists. Claude updates the notes, or says the step is still in progress. It reports the same findings only once.
  • Notes stay small. A note that grows past about 10 KB is split by part into Systems/<System>/ with a small hub note, so an edit points at a small note.
  • Notes describe the present. They are edited in place; history lives in Git.

The working loop ​

  1. /next-system prints Status.md and, when Next names a build order step ("[[Combat Build Order]] step 4"), only that step's plan. Claude reports where things stand and offers to start.
  2. Build the step, checked against its Check.
  3. The step close (the vault-notes skill): update the step's notes, record the check, add the row to Done.md, rewrite Status.md, shrink the step to one line in the build order. Done when docs-check is silent.
  4. /verify before logging off: types, formatting, lint, git, unit tests, and Status against the git log and Done.md.

Design and ideas ​

You say...What happens
a change to a mechanic that has a Design/ noteClaude edits that note and its index row (the design-talk skill)
a new idea (/idea <text>, or just saying it)it is filed in Brainstorm/, then Claude grills you on it with clickable questions; when it is decent it is promoted to a Design/ note, linked both ways
"what if", comparisonsanswered in chat, saved only if you ask

/next-design and /next-brainstorm report where the design and the idea pipeline stand.
