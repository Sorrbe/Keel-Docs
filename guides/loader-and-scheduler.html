Loader and Scheduler ​

How Services, Controllers and Systems get started and updated. The Loader boots them in dependency order. The Scheduler runs their Update at a set rate and their PreSimulation / PreRender hooks every frame. Guard is the small helper both use to call module code safely. All three live in ReplicatedStorage.Keel.

Writing a module ​

Put a ModuleScript in Server/Services, Server/Systems, KeelServer or Client/Controllers (subfolders are fine). It returns a table shaped like Types.Module:

luau
local CombatService = {
	Name = "CombatService",           -- required, unique; keep it the same as the file name
	Dependencies = { "DataService" }, -- optional: Names that must Init/Start before this one
	Hz = 10,                          -- optional: call Update 10 times per second
	Offset = 0.5,                     -- optional, 0 to 1: shift Updates by half a period
}

function CombatService:Init() end     -- wire up; must not wait or call other modules
function CombatService:Start() end    -- may wait and use dependencies
function CombatService:Update(dt) end -- must not wait; only runs if Hz is set

return CombatService

Two more optional hooks run every frame, at fixed points in Roblox's frame (no Hz). Added in 0.3.0:

luau
function MovementController:PreSimulation(dt) end -- before physics: set velocities here
function CameraRig:PreRender(dt) end              -- before drawing, client only: the camera

Which hook? ​

Roblox's frame runs PreSimulation, then physics, then Heartbeat, then PreRender, then draws.

HookWhenUse it forUnity's closest
PreSimulation(dt)every frame, before physicsanything physics must see this frame: a character's velocity, forcesFixedUpdate, but dt is the frame's real step, not fixed (Roblox has no fixed-step hook)
Update(dt) with HzHz times a second, on Heartbeat, after physicsrepeating game work: AI, regen, timers, pollingUpdate
PreRender(dt)every frame, just before drawing; client onlythe camera and visuals that follow what moved this frameLateUpdate

A velocity set in Update reaches physics only on the next frame (a frame of input lag), and a camera moved in Update or PreSimulation can trail the character by a frame. That is what the two frame hooks are for.

Modules still require each other directly. Dependencies only controls the order.

Helpers: a ModuleScript inside another ModuleScript (Name/init.luau plus children) is a helper, not loaded by the Loader. Use that for a module's private parts. Which scripts count (and the skipped Tests and Vendor folders) is decided by Modules.Collect, shared with Defs.Boot and Entity.Boot.

The Loader ​

luau
Loader.Boot("Server", folderA, folderB, ...) -- nil folders are skipped
  1. Requires every ModuleScript in the folders, going into plain Folders, except Folders named Tests or Vendor.
  2. Sorts so each module comes after its Dependencies. Ties go alphabetically, so the order never changes between runs.
  3. Init each module in that order.
  4. Start each one in that order, each in its own thread.
  5. When a module's Start returns, the Scheduler starts its hooks: Update (if it has Hz), PreSimulation and PreRender (if it has them).

Behaviour to rely on ​

  • Init order is dependency order. When your Init runs, your dependencies' Inits have finished.
  • Start does not wait for your dependencies' Start to finish. All Starts are launched in order, and one that waits does not hold back the rest. If you need something a dependency sets up in its Start, wait for it (for example a Signal it fires).
  • Update, PreSimulation and PreRender begin only after your own Start returns.
  • Init must not wait. One that does is reported as an error (Init waited). The rest of that Init still runs later.
  • Timings are logged at Info: [Loader] Init DataService (0.05 ms), Start ..., Server booted N modules.

What stops the boot ​

These are code mistakes you will see in Studio:

  • a dependency cycle: Loader: dependency cycle: A -> B -> C -> A
  • a Dependencies name no module has (a typo)
  • a module with no Name, or two modules with the same Name
  • an Hz that is not a positive number, or Dependencies that is not a list
  • a PreSimulation or PreRender that is not a function, or a PreRender on the server (there is no rendering there)

What is only reported ​

One broken module never stops the game. A module that errors while loading, in Init or in Start is skipped from then on, and modules depending on it get a warning. The Loader also warns about Hz without Update, Update without Hz (it would never run), and a Name that differs from the file name.

The Scheduler ​

Runs from one connection per hook on each side (Heartbeat for Update, PreSimulation, PreRender). The Loader adds modules; game code rarely calls it directly. See Scheduler.Add, AddFrame and Remove.

Update:

  • dt is the real time since that module's last Update.
  • Update runs at most once per frame. An Hz above the frame rate just means "every frame".
  • Offset (0 to 1) shifts a module by that fraction of its period. Give two heavy modules with the same Hz different offsets to put them on different frames.
  • Catch-up cap: after a lag spike, a late module runs on each following frame until it is back on schedule. If it falls more than 3 periods behind, the backlog is dropped, so a spike never causes a burst of stacked Updates.

PreSimulation and PreRender:

  • Run every time Roblox fires that event (normally once per frame), with the event's own dt. No Hz, no Offset, no catch-up.
  • Under load, PreSimulation can fire a little less often than Heartbeat. Use dt; never count calls to measure time.
  • The order of modules within one hook is not guaranteed. If two pieces of per-frame work must run in a set order, put them in one module.

All three hooks:

  • Errors and slow calls (over 4 ms) are logged as errors, named by hook (CombatService.Update: …). A broken hook never stops other modules, or later calls of itself. To avoid flooding the output every frame, each hook logs at most once per 5 seconds, then reports … N more problems since the last report.
  • A hook that waits is stopped: it is logged (… waited, so it was stopped) and that hook is removed from the Scheduler. Put waiting work in task.spawn.

Guard ​

Guard.Call(onError, fn, ...) returns ok, yielded, seconds. It runs fn in its own thread inside xpcall:

  • ok is false if fn errored before returning or waiting.
  • yielded is true if fn waited instead of returning. The rest of fn then carries on in its own thread.
  • onError(message) gets the error with a traceback, even when the error comes after a wait.

This is how the Loader and Scheduler detect "must not wait" breaks without one module freezing the others. See Guard.
