Player data ​

Each player's saved data is loaded when they join, autosaved while they play, saved when they leave, and never empty or shared with another server. It wraps ProfileStore (a pinned copy).

FileWhat it is
KeelServer/Data/init.luauthe Service (Data): loading, kicking, autosave, environment store names, FreshData, Get, Wait, Loaded, Leaving
KeelServer/Data/Migrations.luauthe upgrade runner: version stamp, ordered steps, refusing newer saves

What a player's data is ​

One plain table keyed by component name, built from every Saved component's Default, plus a version stamp:

luau
{ _Version = 1, Currency = { Cash = 0 }, KeelReceipts = { Ids = {} } }

Plain data only: numbers, strings, booleans, tables of those, string keys, no sparse arrays. Change it only on the server. A saved component with an Audience is also sent to clients: write it with Replica.Set, which changes this same table.

Using it ​

luau
local Data = require(ServerScriptService.KeelServer.Data)   -- a Service: add "Data" to Dependencies

Data.Loaded:Connect(function(player, data) end)    -- data is ready (also fires for players already in)
Data.Leaving:Connect(function(player, data) end)   -- just before the final save; must not yield

local data = Data.Get(player)    -- nil while loading or after leaving
local data = Data.Wait(player)   -- yields; nil if the player left or the load failed
data.Currency.Cash += 10         -- saved automatically

Data.SaveNow(player, confirm?)   -- yields until a save holding the change is confirmed; false if it cannot be

Server/Main calls Data.Configure({ TestPlaceIds = Rules.TestPlaceIds, Migrations = require(Server.Migrations) }) before Loader.Boot.

Behaviour to rely on ​

  • Store name by environment: PlayerData_Studio in Studio, PlayerData_Test on a place listed in Rules.TestPlaceIds, PlayerData_Live anywhere else. A test place can never write live data.
  • DataVersion: a whole-number attribute on ServerScriptService. Absent or 1 keeps the plain store name; 2 or more adds _vN (PlayerData_Live_v2), so bumping it starts everyone on a brand-new, empty store. The old store is left untouched, so setting it back restores those saves.
  • Loading waits for Entity.Boot, because the template must include every saved component. Then it starts the session, runs the migrations, and fills in missing fields from the template.
  • Kick on failure: no session, a failing migration, or a save from a newer version kicks the player with a message and logs the reason. Nobody plays on empty data.
  • Left while loading: the session is released at once. Another server takes the session: the player is kicked.
  • Autosave every 60 seconds, a save on leave, and a save on shutdown that ProfileStore waits for.
  • Data.SaveNow saves at once and yields until a save that holds the change has finished, or 30 seconds pass. It returns false if the session is over or nothing confirmed in time. Use it before granting something that must not be lost or granted twice.
  • FreshData (Studio only): set the attribute FreshData = true on ServerScriptService. Every player then starts with brand-new data in a throwaway in-memory store; the real saves are never read or written.
  • Studio without API access uses ProfileStore's mock store, so nothing is saved.

Migrations ​

Migrations.Run(data, steps) upgrades a copy of a save. Step N turns a version N-1 save into version N, so the current version is the number of steps. Only ever append steps: never edit or reorder one that has shipped.

luau
-- Server/Migrations.luau
return {
	function(data) -- step 1: Cash moved into Currency
		data.Currency = { Cash = data.Cash }
		data.Cash = nil
	end,
}
  • A brand-new (empty) profile is stamped with the current version and runs no step.
  • A non-empty save with no version counts as version 0.
  • A step that errors, a version that is not a whole number, or a save newer than the server knows returns nothing, and the player is kicked. The saved data is left untouched (steps run on a copy), so fixing the step and rejoining works.
  • Missing fields are filled in after the steps run.

See the Data and Migrations API pages.
