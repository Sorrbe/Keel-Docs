Entities and components ​

Things with identity and behaviour (a player, an NPC, a door, a plot) are entities. Their behaviour lives in components (Health, Door, Currency) attached to them, so a player and an NPC can share the same Health code. A component can attach itself to every Instance carrying a CollectionService tag, and detach when it is destroyed, loses the tag or streams out.

Defining a component ​

One module per component, in Server/Components/ or Client/Components/. It returns what Entity.component returns:

luau
local Door = { Name = "Door", Tag = "Door" }

function Door:Attach()
	-- self.Instance  the tagged Instance;  self.Entity  its entity (self.Entity.Id)
	-- self.Trove     cleaned on detach: put every connection and effect in it
	self.Trove:Connect(self.Instance.Touched, function() end)
end

return Entity.component(Door)
FieldMeaning
NameThe component's kind ("Door"), unique on this side. It is not an Instance's name: many doors share it. Saved data is keyed by it.
TagOptional. Every Instance with this tag gets the component, now and later.
AttachOptional. Runs when attached. Must not wait (use task.spawn). If it errors, the error is logged and the component is not attached.
AudienceOptional: "Owner", "Public" or "None", for player state clients may see. Needs Default. See State and Replica.
Saved, DefaultFor components holding player data. Saved = true needs Default (plain data), and so does an Audience; a Default with neither Saved = true nor an Audience errors. Entity.Template() returns a copy of every saved Default keyed by Name, which player data builds each profile from.

Entity adds Door.Added and Door.Removed (Signals, fired with the component), Door.GetAll() and Door.Of(instance). A component cannot define those names itself.

Entities and ids ​

luau
local entity = Entity.of(player)   -- get or create the entity of an Instance
entity.Id                          -- unique string, never derived from the Instance's name
Entity.byId(id)  Entity.get(instance)   -- find one, nil if none
entity:Add(Currency)               -- attach; returns the component (the existing one if already attached)
entity:Get(Currency)  entity:Remove(Currency)   -- the component / detach (false if not attached)
entity:Destroy()                   -- detach everything; entity.Destroyed fires

Identity never comes from a name, since names collide:

  • A Player is player_<UserId> on both sides.
  • Any other Instance gets e<n> on the server, which writes it to the Instance's EntityId attribute (always overwritten, so a clone never keeps its source's id). The client reads that attribute, so the server and client entity of one door share an Id.
  • A client-only Instance with no server twin gets client_<n>.

Behaviour to rely on ​

  • Boot: Server/Main and Client/Main call Entity.Boot(Components folder) after Loader.Boot, so Services have connected to Added before the first components attach. A component defined after Boot starts watching immediately. Entity.WaitForBoot() yields until Boot has run; a Service that needs every component defined, like Data, calls it in Start.
  • Attach runs once per Instance and component. Adding twice returns the first component.
  • Detach always cleans the component's Trove. A failing cleanup is logged, never thrown. Removed fires after the cleanup.
  • An entity destroys itself when its Instance is destroyed, a moment later (Roblox's Destroying signal is deferred).
  • Streaming: a tagged Instance leaving the DataModel detaches the client component, and streaming back in attaches a fresh one with the same Id. The server's component is unaffected. The Instance's children may not have streamed in when Attach runs: use WaitForChild inside a task.spawn, or guard for nil.
  • Separate sides: server and client each have their own components and may reuse a Name.
  • Entity.newWorld() makes a separate registry for tests.
