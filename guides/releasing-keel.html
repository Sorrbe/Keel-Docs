Releasing Keel

On this page

Releasing Keel ​

Keel is changed in its own repository and released as a Git tag. A game never edits Keel; it updates to a tag.

What is Keel's and what is the game's ​

keel.manifest.json in the Keel repo lists both. See What gets created for the full split.

Release a version ​

  1. Work in the Keel repo. It is also Keel's own test place: connect Script Sync there. Never edit Keel inside a game; the keel-guard hook refuses it.

  2. Run the unit tests ([Tests] N passed, M failed) and the /verify skill. See Unit tests.

  3. Bump VERSION and add a CHANGELOG.md entry. Patch for fixes, minor for new features, major when a game must change its own code.

  4. Commit, then tag with a description and push. Every tag is annotated with a one-line description of what changed; the tag-check hook refuses a tag without one, and the docs workflow won't publish it:

    sh
    git tag -a v0.2.0 -m "Keel 0.2.0: <what changed, one line>"
git push origin v0.2.0   # or: git push --tags

  5. The docs publish themselves. Pushing the tag starts the "Publish docs" workflow, which checks the tag's description, rebuilds the site and updates the public docs repo with the description as its commit message. Check the Actions tab on GitHub for a green tick. (If the workflow can't run, npm run publish-docs in site/ does the same by hand.) For a major version, the "Release (majors only)" workflow also creates the GitHub Release (see below).

  6. In each game: node tools/keel.js update v0.2.0. See Update Keel.

Tags and GitHub Releases ​

Every version is a Git tag. Only a major version also gets a GitHub Release.

VersionTagGitHub Release
Patch (v1.3.2) or minor (v1.3.0)yesno: CHANGELOG.md and this site's changelog describe it
Any 0.x versionyesno
Major (v1.0.0, v2.0.0)yesyes, created automatically when the tag is pushed

A major is the one update that asks a game to change its own code, so it gets a page of its own. Its notes are built from CHANGELOG.md by .github/scripts/release-notes.mjs: that version's section first (read its Migration first), then every version since the previous major, newest first. A major tag with no ## N.0.0 section in CHANGELOG.md makes the workflow fail on purpose.

Nothing reads Releases: keel.js installs from tags, and update latest takes the newest tag. GitHub's "Latest release" can therefore show an older major than the newest tag; each Release's notes say so.

Every change must be documented ​

A change is not finished until its documentation is updated in the same release. That covers the CHANGELOG.md entry, the hand-written pages (guides, tutorials, cheat sheet, FAQ, troubleshooting), the Luau header comments and site/api-notes/ that the API Reference is generated from, and Keel's notes in Docs/Systems/. Run npm run check in site/ before tagging.

What each kind of change needs:

ChangeDocumentation required
New feature or moduleA changelog entry; a guide section or page; an API page (add it to GROUPS in site/scripts/gen-api.mjs, with a header comment and api-notes/); a row in the cheat sheet.
New kit (when kits arrive)All of the above, plus its own VERSION, what it depends on, and how a game adds it. Kits are optional add-ons, so say clearly that a game does not get one unless it installs it.
DeprecationThe old API keeps working. Mark it deprecated in its header comment and in api-notes/, say what replaces it and what to change in the game, and add a Deprecated line to the changelog. Remove it only in a later major version, and say so in advance.
Behaviour changeA changelog entry saying what differs and what a game should check. Update every page that described the old behaviour.
Breaking changeA major version bump, and a Migration section in the changelog entry that tells a game exactly what to change in its own code.
RemovalOnly in a major version, after at least one release that deprecated it. List it under Removed in the changelog.
FixA changelog entry. Update any page or troubleshooting item that described the bug or its workaround.

Changelog entries ​

Group each version's entry under these headings, leaving out any that do not apply: Added, Changed, Deprecated (still works, but update your game), Removed, Fixed, Migration (what a game must do). Write them for someone deciding whether to run update.

Deprecation example ​

md
## 0.3.0
### Added
- `Net.stream` for large replaceable payloads.
### Deprecated
- `Net.unreliable` is now `Net.stream`. `Net.unreliable` still works and logs a warning once; switch to `Net.stream` in your Shared/Net list.

Behaviour to rely on ​

  • update overwrites owned files in place and deletes a file Keel dropped, but never deletes an owned folder (that would break Script Sync), so a dropped file disappears from the game.
  • Hashes ignore line endings, so a checkout on another machine does not look like an edit.
  • Nothing at runtime reads the version; it lives only in keel.json and VERSION.
  • keel.js new and update take the newest v* tag when you give none or say latest.

Trying a change before tagging ​

keel.js accepts --from <path> to use a local Keel checkout instead of cloning from GitHub:

sh
node tools/keel.js update latest --from ../Keel

This documentation ​

These docs live in site/ in the Keel repo. The API pages are regenerated from the source on every build, and the changelog page from CHANGELOG.md, so a release needs no extra docs step beyond updating the hand-written pages when behaviour changed. See site/README.md.
